# Backup v0.1

## Arquitectura

La interfaz arma el archivo. Rust solo hace lo que el webview no puede hacer de forma segura: snapshot de la base abierta, leer documentos, escribir la ruta elegida por el usuario y cambiar los archivos en uso.

Crear backup:

1. El diálogo nativo elige la ruta.
2. `VACUUM INTO` escribe un snapshot en `backup-work/`.
3. Se leen ese snapshot y los archivos de `documents/`.
4. TypeScript genera el zip.
5. Rust escribe el zip en la ruta elegida y borra el snapshot.

Restaurar:

1. Se lee el zip y se valida en memoria. Si falla, no se escribe nada.
2. Si ya hay cartera o documentos, se crea antes un zip de seguridad en `backups/`.
3. Los archivos validados se copian a `restore-staging/`.
4. Rust abre la base staged, corre `foreign_keys`, `quick_check` y exige las migraciones `001` y `002`.
5. Se cierra el pool, se hace checkpoint y se intercambian los archivos.
6. Se vuelve a abrir la base. Si el health check falla, se deshacen los renombres.

`backups/`, `backup-work/` y `restore-staging/` no entran en el zip del usuario.

## Formato

Un zip sin comprimir (método 0):

- `manifest.json`
- `cartera.db`
- `documents/...`

Nombre sugerido: `analisis-cartera-backup-YYYY-MM-DD.zip`.

El manifest tiene `backupVersion` 1, `appVersion`, `createdAt`, `databaseFile`, `documentsDirectory` y `appIdentifier` (`com.analisiscartera.app`). No lleva cifras de la cartera.

Tope: 200 MB. Se rechazan rutas con `..`, absolutas o con barra invertida.

## Snapshot

No se copia `cartera.db` mientras el pool lo tiene abierto. El snapshot es `VACUUM INTO` sobre una conexión del pool de sqlx. El destino no puede existir; si quedó uno anterior, se borra antes. `VACUUM INTO` no corre dentro de una transacción y deja un archivo consistente aunque haya escrituras posteriores: esas escrituras no entran en el snapshot.

Al cerrar el pool se ejecuta `PRAGMA wal_checkpoint(TRUNCATE)` y se eliminan `-wal`, `-shm` y `-journal`, para que un WAL viejo no se reaplique sobre la base restaurada.

Si `VACUUM INTO` falla, la restauración se aborta y el archivo actual queda donde está.

## Restore fallido

La validación ocurre antes del intercambio. Un manifest de otra versión, otro identificador, una base que no es SQLite o que no pasa `quick_check` no reemplaza los datos.

El intercambio son dos `rename` (base y documentos). En Windows eso no es una transacción del sistema de archivos. Si el proceso muere entre los dos, quedan `cartera.db.previous` y `documents.previous`, más el zip previo en `backups/`. Si el health check posterior falla, esos `.previous` vuelven a su lugar. Si el health check pasa, se borran.

Una instalación vacía no exige copia previa. Una instalación con datos sí: sin ese zip, `commit_restore` no intercambia archivos.

Restaurar el mismo backup otra vez vuelve a dejar la misma cartera. No es un no-op, pero el resultado queda consistente.

## Health

Al arrancar se abre la base, se aplican migraciones y se comprueba `foreign_keys = 1`, `PRAGMA quick_check = ok` y las versiones `001` y `002`. Si el archivo ya existe, la conexión no lo recrea. Un fallo cierra el pool, conserva el archivo y muestra el error. La ventana igual abre, para poder restaurar desde Datos.

Un PDF ausente se informa y no bloquea el arranque. No se borran filas.

## SQL

`db_select`, `db_execute` y `db_transaction` siguen registrados porque los repositorios los usan. El webview no puede mandar otra cosa que una sentencia `SELECT`, `INSERT` o `UPDATE`. Quedan rechazados `ATTACH`, `VACUUM`, `PRAGMA`, `DROP`, `ALTER`, `CREATE`, `DELETE` y sentencias múltiples. Backup, restore y health usan comandos con nombre.

## Rutas

Identificador: `com.analisiscartera.app`. No se migra una base de `com.tauri.dev`.

- Base: `app_config_dir/cartera.db`
- Documentos: `app_data_dir/documents/`
- En Windows ambas carpetas son `%APPDATA%\com.analisiscartera.app`
- En Linux la base va a la config de XDG y los documentos a data de XDG

Versión de la app: `0.1.0`. `ENGINE_VERSION` sigue en `1`.

## Límites

Sin cifrado, sin nube, sin rangos históricos. El zip no comprime. El intercambio en Windows no es atómico. Un import concurrente con la restauración puede fallar porque el pool se cierra. Si la base está corrupta y `VACUUM INTO` no puede leerla, no hay restore automático: el archivo queda para una copia manual de la carpeta.
